# ADR-004: Double Ratchet Protocol for Forward Secrecy

**Status:** Accepted  
**Date:** 2026-03-24  
**Authors:** Trustline Engineering

## Context

The initial implementation used a single X3DH shared secret for all messages in a conversation. While X3DH provides mutual authentication and key agreement, reusing the same key for multiple messages means that compromising a single key exposes the entire conversation history.

## Decision

Implement the **Signal Protocol's Double Ratchet algorithm** on top of X3DH:

1. **Implementation:** `crates/crypto_core/src/ratchet.rs` — a pure-Rust implementation using HKDF-SHA256 for KDF chains and ChaCha20-Poly1305 for AEAD.
2. **Session lifecycle:**
   - Sender calls `RatchetSession::init_as_sender(shared_secret, bob_spk)` after X3DH.
   - Receiver calls `RatchetSession::init_as_receiver(shared_secret, spk_pub, spk_priv)`.
   - Each `encrypt()` / `decrypt()` call advances the ratchet, deriving a unique message key.
3. **Session persistence:** Ratchet session state (JSON-serialized `RatchetSession`) is stored in the local SQLCipher vault keyed by `conversation_id`.
4. **Tauri commands:** `ratchet_init_sender`, `ratchet_init_receiver`, `ratchet_encrypt`, `ratchet_decrypt` expose the ratchet operations to the frontend via IPC.
5. **Wire format:** Each message includes a `ratchet_header` (DH public key, previous chain counter, message counter) alongside the ciphertext.

## Consequences

- **Positive:** **Forward secrecy** — compromising a future key does not expose past messages.
- **Positive:** **Post-compromise security** — the ratchet self-heals within one DH round-trip after key exposure.
- **Positive:** Per-message unique keys prevent bulk decryption.
- **Negative:** Session state must be persisted after every send/receive — losing state makes future messages undecryptable.
- **Negative:** Out-of-order message handling requires maintaining a skipped-keys cache (implemented in `ratchet.rs`).
