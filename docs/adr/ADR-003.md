# ADR-003: PostgreSQL Row-Level Security for Tenant Isolation

**Status:** Accepted  
**Date:** 2026-03-15  
**Authors:** Trustline Engineering

## Context

Trustline is a multi-tenant platform where multiple organizations share the same database infrastructure. Cross-tenant data leakage — even of encrypted blobs — would be a critical security failure. Application-level tenant filtering (`WHERE org_id = ?`) is fragile and prone to developer error.

## Decision

Tenant isolation is enforced at the **database layer** using PostgreSQL Row-Level Security (RLS):

1. All tenant-scoped tables (`users`, `devices`, `one_time_pre_keys`, `encrypted_messages`, `audit_logs`) have RLS policies: `USING (org_id = current_setting('app.current_org_id')::uuid)`.
2. The backend sets the RLS context per transaction via `SET LOCAL app.current_org_id = $1` before executing any tenant-scoped query.
3. The `db.rs` module provides a `with_rls_context(pool, org_id, closure)` helper that wraps queries in a transaction with the RLS variable set.
4. Migration `006_enable_rls.sql` enables RLS on all tenant tables; migration `014_force_rls.sql` sets `FORCE ROW LEVEL SECURITY` to ensure the policies apply even to table owners.

## Consequences

- **Positive:** Cross-tenant data access is **impossible** at the SQL level — even a bug in application code cannot bypass the policy.
- **Positive:** Every query is automatically scoped — developers don't need to remember `WHERE org_id = ?`.
- **Negative:** Requires careful transaction management — every query must run within a context that has `app.current_org_id` set.
- **Negative:** Global admin queries (e.g., cross-org analytics) need an explicit `SET LOCAL` bypass, adding complexity.
